# Sessions

Every visitor to a catalog gets a **session**: a server-side data structure
that persists between requests and carries their identity, form values,
scratch state, and shopping carts. Sessions are what turn stateless HTTP
into a shopping trip. This chapter covers what lives in a session, how
session ids are issued and protected, the storage backends, and expiry.
How the id is resolved on each request is described step-by-step in
[Architecture](architecture.md); this chapter picks up from there.

## What is in a session

`init_session()` (`lib/Vend/Session.pm`) creates each new session with:

| Key | Exposed as | Purpose |
|-----|-----------|---------|
| `values` | `$::Values`, `[value ...]` | user form values — name, addresses, choices — persisted across requests; seeded from [ValuesDefault](../config/ValuesDefault.md) |
| `scratch` | `$::Scratch`, `[scratch ...]` | working state for pages: flags, computed bits; seeded from [ScratchDefault](../config/ScratchDefault.md) |
| `carts` | `$::Carts`, `[item-list]` | all shopping carts (`main` plus any named carts) |
| `discount_space`, `levies` | `$::Discounts` | discounts and assessed charges |
| `host`, `ohost`, `shost`, `browser`, `referer` | — | client identity for verification |
| `source` | — | affiliate/ad source ([SourcePriority](../config/SourcePriority.md)) |
| `username`, `logged_in` | `[data session ...]` | set at [UserDB](user-database.md) login |
| `last_url`, `history` | `[history-scan]` | recent pages when [History](../config/History.md) is on |

The functional difference to internalize: **values** are the visitor's
durable answers (they survive and pre-fill forms); **scratch** is yours to
compute with (control flow, page options). `[value name]` writes need a
form submission or `[value name=... set=1]`; scratch is set freely with
`[set]`/`[seti]`. CGI variables (`[cgi ...]`) are neither — they exist for
the current request only.

A `SpecialSub init_session` hook runs for each new session if configured.

## Session ids and cookies

A new visitor receives a generated id (`MV_SESSION_ID` cookie by default);
the id also rides in URLs generated by `[page]`/`[area]` for cookie-less
clients (`mv_session_id`). Protections, all tunable per catalog:

- **Host binding** — a session is only honored from the IP it was created
  at (`ohost`; the TLS-side `shost` separately), unless the id came from a
  cookie; [WideOpen](../config/WideOpen.md) disables the check entirely,
  [DomainTail](../config/DomainTail.md)/[IpHead](../config/IpHead.md)
  loosen it for proxy farms.
- **Robot handling** — recognized crawlers
  ([RobotUA](../config/RobotUA.md)/[RobotIP](../config/RobotIP.md), the
  shipped `robots.cfg` lists) share one throwaway session so spiders don't
  bloat the store; [RobotLimit](../config/RobotLimit.md) locks out
  request floods; excessive new-session creation from one IP draws a 403.
- **Custom cookies** — [CookieName](../config/CookieName.md) renames the
  cookie; [Cookies](../config/Cookies.md)/[CookieDomain](../config/CookieDomain.md)
  control issuance; `mv_tmp_session=1` forces a throwaway session (used
  by probes and some AJAX); [CookieLogin](../config/CookieLogin.md) allows
  "remember me" logins.

Session state is written back at request end; concurrent requests in the
same session serialize on the session lock (file backends) or database
transaction.

## Storage backends

[SessionType](../config/SessionType.md) selects the store
(`%Session_class` in `lib/Vend/Session.pm`):

| Type | Storage | Notes |
|------|---------|-------|
| `File` (default) | one file per session under `session/`, hashed into subdirectories ([SessionHashLevels](../config/SessionHashLevels.md)/[SessionHashLength](../config/SessionHashLength.md)) | simple, fine for most stores |
| `NFS` | as `File`, lock strategy suited to NFS mounts | for shared filesystems |
| `GDBM` / `DB_File` | single DBM file ([SessionDatabase](../config/SessionDatabase.md)) | legacy; whole-file locking |
| `DBI` | a `sessions` SQL table | multi-server setups; strap ships table definitions (`dbconf/*/sessions.*`) |
| `Redis` | a Redis server (`Vend::SessionRedis`) | multi-server, fast expiry |

Sessions serialize via Storable when available (the installer's
`_session_storable` marker), falling back to Perl `uneval`. For busy or
load-balanced deployments prefer `DBI` or `Redis` — see
[Performance](performance.md). Utility scripts for inspecting and
migrating session stores live in `eg/` (`ic-session-print`,
`migrate-sessions-to-dbi`).

## Expiry and housekeeping

[SessionExpire](../config/SessionExpire.md) (strap: `4 hours`) is how long
an idle session stays valid; an expired id gets a fresh session. Expired
File/DBM sessions are reaped by the daemon's housekeeping pass and the
`expire` utility (`bin/expireall`, `bin/expire` — see
[Installation](installation.md)); DBI/Redis stores expire rows natively.
Do not confuse session expiry with login state: [UserDB](user-database.md)
logins live inside the session and end with it (or at
`[logout]`).

Sizing note: everything you stuff into values/scratch/carts is
serialized and rewritten every request. Keep big blobs (search results,
generated HTML) out of the session; use [timed-build](../tags/timed-build.md)
or scratch-free approaches instead.

## Working with the session from pages and code

    [value fname]                 read a value
    [set checkout_stage]ship[/set]     set scratch
    [data session username]       read any session key
    [dump]                        the whole session, for debugging

From Perl: `$Session`, `$Values`, `$Scratch`, `$Carts`
([Embedded Perl](perl-embedding.md)). Multiple independent value spaces
are available via `mv_values_space`, and `[value-extended ...]` handles
structured/file values — see the tag reference.
